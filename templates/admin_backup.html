How to actually keep this safe

  1. Tap the button above — your browser downloads a .zip file straight to your phone or computer.
  2. Move that file somewhere off this server — Google Drive, WhatsApp-to-self, email to yourself, a laptop folder. A backup that lives only on the same server it's protecting isn't a real backup.
  3. Do this regularly — weekly is a reasonable minimum for a live business; after any big change (price update, new profiles approved) is a good extra trigger.
  4. Keep at least 2–3 recent backups, not just the newest one — if a backup turns out to be corrupted or taken mid-problem, you still have an earlier good copy.

How to restore

  1. Unzip the backup — you'll get matrimonial.db plus folders like profile_originals/, payment_proofs/, banners/, etc.
  2. Stop the running app (or put it in maintenance) before restoring, so nothing writes to the database mid-restore.
  3. Replace the server's matrimonial.db with the one from the backup, and put each folder back under the server's data directory in the same structure it came from.
  4. Restart the app and check /healthz, then spot-check a few profiles and the admin dashboard before trusting it's fully back.

Test your restore process at least once

A backup you've never restored from is a guess, not a plan. Periodically — not necessarily every week, but at least once when you set this up, and again after any major change to this app — actually try restoring a backup into a separate test copy of the app (not the live one) and confirm the data comes back correctly. If you don't have a safe place to test this yourself, this is worth asking a developer to walk through with you once.

Why this matters more than it might seem

Whether this hosting setup keeps your database and uploaded files permanently, or wipes them on every redeploy, has never been confirmed. Until that's checked and confirmed safe, treat every deploy/restart as a risk and download a fresh backup before you deploy any change, not just on a routine schedule.
